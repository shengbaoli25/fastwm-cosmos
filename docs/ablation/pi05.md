# π0.5 / RM71D78

This adapter calls the [official OpenPI](https://github.com/Physical-Intelligence/openpi/tree/215abfb217dbac7d5f1273282331b9b1866c0479)
JAX model, optimizer, trainer, Orbax checkpoints, and trained-policy loader. It
does not implement a substitute network. The pinned revision is
`215abfb217dbac7d5f1273282331b9b1866c0479`.

The starting checkpoint is the official `gs://openpi-assets/checkpoints/pi05_base`
(download separately). The training command records a SHA256 of its local
`params/` tree. This source URI is not an immutable weight checksum: the exact
downloaded bytes become part of the run binding before training starts. No base
weights were downloaded and no training was started by this change.

## Environment

Use a separate Linux environment for this baseline. Follow the pinned OpenPI
`uv.lock` rather than the parent repository's Torch/Transformers environment.
The pinned project uses Python >= 3.11, JAX CUDA 12 `0.5.3`, Flax `0.10.2`, and
LeRobot commit `0cf864870cf29f4738d3ade893e6fd13fbd7cdb5` (v2.1 API).

```bash
git clone https://github.com/Physical-Intelligence/openpi /work/upstream/openpi
git -C /work/upstream/openpi checkout 215abfb217dbac7d5f1273282331b9b1866c0479
git -C /work/upstream/openpi submodule update --init --recursive
cd /work/upstream/openpi
GIT_LFS_SKIP_SMUDGE=1 uv sync --frozen
```

Commands below run from the root of **fastwm-cosmos**, using that upstream
environment's Python. The adapter checks the Git revision and rejects tracked
upstream modifications. It adds the pinned `src/` to the current process only.

## Recipe and data contract

The shared exporter supplies a verified local LeRobot v2.1 dataset, including
the original 78-episode provenance. Discontinuous valid segments are separate
exported episodes. All source trajectories are used for training fit; this is
not a held-out generalization evaluation.

- Current `global` and `wrist` RGB are mapped to `base_0_rgb` and
  `left_wrist_0_rgb`. The unused right wrist is zero and masked.
- Measured absolute joint8 is the state. Training subtracts current state from
  the seven joint targets with the **official** `DeltaActions` transform;
  gripper targets remain absolute. `AbsoluteActions` reverses this at inference.
- Official π0.5 quantile normalization, letterboxed 224 x 224 resizing, prompt
  tokenization, discrete state tokens, and 32-dimensional padding are retained.
  The model predicts 32 frames; the first eight output channels are the robot
  action. The server receives radians and gripper openness in `[0,1]`.
- Force is not passed into this baseline. Invalid output shape and non-finite
  output cause an error. The common server applies the physical `[0,1]` gripper
  bound; the model adapter does not alter angles.

Default planned recipe: LoRA on the official PaliGemma and action expert,
50,000 optimizer updates, global batch 8, seed 42, save/keep every 5,000 updates,
no EMA for LoRA, and the official default AdamW/cosine schedule (1,000 warmup,
peak `2.5e-5`, decay to `2.5e-6` over 30,000 steps). `finetune_mode: full` uses
the same official model without LoRA and EMA 0.99. These are adaptation settings,
not a claim to reproduce the official LIBERO benchmark recipe.

Reserve one 80 GB CUDA GPU for initial validation; the upstream general guidance
lists >22.5 GB for LoRA and >70 GB for full finetuning, but these are not measured
budgets for this 32-frame, batch-8 recipe. Multi-GPU sharding is available through
`fsdp_devices`; global batch must divide the visible device count. No Windows
JAX GPU training support is claimed.

## Configuration and commands

Example `pi05-run.json` (replace paths with real local assets):

```json
{
  "upstream_root": "/work/upstream/openpi",
  "dataset_root": "/work/data/rm71d78_lerobot21",
  "run_root": "/work/runs/pi05-rm71d78",
  "pretrained_checkpoint_path": "/work/weights/pi05_base",
  "finetune_mode": "lora",
  "num_train_steps": 50000,
  "batch_size": 8,
  "save_interval": 5000,
  "seed": 42,
  "num_workers": 2,
  "fsdp_devices": 1
}
```

```bash
# Pure plan: does not import JAX, create directories, download, or train.
/work/upstream/openpi/.venv/bin/python scripts/ablation/pi05.py --config pi05-run.json

# Explicit statistics preparation; loads the actual exported images/data and
# uses the official statistics script. May fetch the small official tokenizer.
/work/upstream/openpi/.venv/bin/python scripts/ablation/pi05.py stats --config pi05-run.json

# Only these explicit commands start optimization. They were NOT run here.
/work/upstream/openpi/.venv/bin/python scripts/ablation/pi05.py train --config pi05-run.json
/work/upstream/openpi/.venv/bin/python scripts/ablation/pi05.py resume --config pi05-run.json
```

Statistics are saved to
`<run_root>/assets/pi05_rm71d78_lora/<dataset_basename>/norm_stats.json`.
`pi05-training-binding.json` binds the dataset manifest identity, exact recipe,
upstream revision, normalization, and (at training start) initial weight digest.
Existing statistics are not overwritten. Resume rejects missing optimizer state,
changed data/normalization/settings, and changed base weights.

Official step checkpoints are saved under
`<run_root>/checkpoints/pi05_rm71d78_lora/train/<step>/`. Each contains `params/`,
`train_state/`, and `assets/<dataset_basename>/norm_stats.json`. Upstream uses
zero-based step labels; inspect actual saved directories rather than assuming
the filename is the total update count.

The adapter's scoped save callback also embeds
`assets/ablation_training_binding.json` in the same Orbax asset transaction.
Deployment requires this embedded binding to equal the external training record,
so matching normalization alone cannot authorize another run or LoRA/full recipe.

For deployment, retain the run settings and add `checkpoint_path`,
`normalization_path` (the **checkpoint's** stats), `training_binding_path`,
`dataset_manifest_sha256`, and optionally `num_inference_steps` (default 10).
The shared deployment exporter/server binds these files and calls
`load_predictor(config)`. The predictor verifies training settings and stats,
then calls the official `create_trained_policy`; it does not need the dataset
files, base weights, or optimizer state on the server. The dataset asset namespace
is read from the binding; `dataset_root` and `run_root` can be omitted when an
explicit `training_binding_path` is supplied.

## Validation status

Local checks cover camera identity, LeRobot/wire image conversion, padding and
the eighth gripper channel, exclusion of force, preservation of input targets,
invalid-output rejection, and the no-training default. They do not validate
official weights, GPU loss/backpropagation, checkpoint restoration, real-data
HTTP replay, latency, or memory. Those checks require the pinned Linux runtime,
actual 78-trajectory export, official weights, and a trained checkpoint.
