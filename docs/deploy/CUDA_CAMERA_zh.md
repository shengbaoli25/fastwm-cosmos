# GB10 Cup 部署：CUDA 捕获冲突与夹爪诊断

2026-10-23，GB10 / ARM64 / Torch 2.9.1+cu130 / NVIDIA 580.173.02。训练权重是 cup joint8 的 step 20000，SHA256 `34efeb39d0079848c09ca4120655ee94ae4fb1950055a73ecf096f4dff560da6`，6,038,120,329 字节。两路 RealSense 输出 640×480 RGB8、30 FPS，机械臂 RM75，夹爪 CTAG2F120。

## 已证实的 CUDA 根因

硬件连接后加载模型时触发 `cudaErrorStreamCaptureInvalidated`。临时 CUPTI 追踪捕获到首个错误是相机原生线程的 `cuMemFree_v2 / cudaFree` 返回 900，随后模型 `cuLaunchKernel` 返回 901。原生调用栈落在 `pyrealsense2` 的 `rscuda::unpack_yuy2_cuda_helper`。这是相机和模型共享进程时的 CUDA Graph 捕获冲突；GB10 capability 12.1 对 wheel 12.0 的提示不能解释该调用栈，实际 BF16 核及模型均能运行。

修复将每路相机放在独立 spawn 进程中，进程间仅传 RGB 字节和元数据，保留官方 RGB 转换、序列号、设备时间、帧号与主机采集时间。模型继续使用 global CUDA Graph 捕获。进程启动失败、退出、关闭和重新启动有明确清理路径；RGB 身份、长度和时间戳会验证。模型加载及捕获体增加完整 traceback。

同进程的 CPU 颜色转换尝试曾短暂运行成功，但后续再次捕获失败，因此不作为最终修复或验收依据。

## 现场验证范围

相机隔离服务在双相机持续出图时完成两轮模型加载，每轮包含服务自带的两次合成预热。随后由现场操作者启动控制，状态记录到 25 个已接受的真实输入推理结果，Video/Force/Action 均使用 CUDA Graph，无 eager 回退，检查期间日志没有新的 CUDA 捕获错误。采样为 16/16/16、同步执行；这不是减步扫描或离线 benchmark，也不代表抓杯成功率或长期稳定性。

另一独立问题仍存在：运行中出现双相机时间差、相机与机械臂时间差超限。相机当时均协商为 USB 2.1。没有放宽 50 ms 相机时差、30 Hz 观测、力反馈新鲜度和滤波身份检查；USB 带宽、调度和 IPC 延迟都需保留为排查方向，不能据此认定 CUDA 再次故障。

## 夹爪过程中松开的调查

用户报告夹爪会松开一些。暂停后的状态是 enabled=true、alarm=0；这只能说明该次读取时没有报警。旧日志没有逐次目标，无法追溯松开瞬间的命令，尚未确认根因。

训练元数据定义 `state[19]` 为测量开度，`action[7]` 为最近已确认下发目标，均为 0 闭合、1 张开。部署保留该连续开度定义，按现有死区 0.02、每次目标最大变化 0.15、最短指令间隔 0.1 s 下发。夹住物体时测量开度通常大于闭合目标；不能把这种差值直接判为电机故障，也不能把力预测当成夹爪电流或实际夹持力。

为下一次现场复现新增：

- 每块 32 个反归一化目标及裁剪值，关联源观测序号和运行 epoch。
- 每次实际成功写入的请求值、限幅后目标、上一目标、开合方向、原始寄存器目标、完成时间及 policy/manual 来源。
- 可选记录既有轮询的实际位置、使能、报警和读取时间；网页显示实际开度、待发目标及已下发值。
- 取消待发目标事件，便于检查同步动作块结束时是否提前取消闭合的剩余限幅过程。

这些改动不增加夹爪 RTU 轮询，也不改变开度、扭矩或采样策略。未加入自动闭锁或开夹滞回，因为它们会改变策略释放物体的行为；应先凭实际命令与反馈判别原因，再单独对比验证。
